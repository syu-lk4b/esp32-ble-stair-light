# 蓝牙楼梯灯逆向记录

这份文档记录 [BLE-PROTOCOL.md](BLE-PROTOCOL.md) 里的协议是**怎么**得到的，
不只是结论。包括中继方案、第一次抓包、命令扫描，以及走过的弯路。

> 所有操作都在自己购买的设备上完成。冒充别人的 BLE 设备是不对的。

## 一句话总结

1. 用 Bleak 扫描，dump GATT：服务 `FFE0`、特征 `FFE1`、无需配对。
2. 厂商 App 只认广播名匹配的设备。想看它的流量，就把自己变成那台设备。
3. **关键技巧**：先连上真机——多数 BLE 模块被连接后会停止广播，手机就只会看到代理。
4. 把手机的写转发给真机，把真机的 notify 转发回手机，并记录每一帧。
5. App 连上后第一件事是发 `BA` 校时；回包里直接带着当前模式、两路亮度和定时。
6. 用 ESP32 直接重放抓到的帧，确认灯真的听话。

## 1. 发现设备

Bleak 扫描到两个设备，广播名是 `upstair` 和 `downstair`，信号约 −72 dBm。
广播的厂商数据里带着模块 MAC（厂商 ID `0x4458`，大夏龙雀 DX-BT24 透传模块）。

不配对直接连接，两台设备的 GATT 完全一致：

| | |
|---|---|
| 服务 | `0000FFE0-...` |
| `FFE1` | read, notify, write, write-without-response |
| `FFE2` | write, write-without-response（AT 指令） |

`FFE1` 就是通往灯控 MCU 的"串口透传"通道，App 的所有操作最终都是这上面的裸字节。

## 2. 核心技巧：让真机"消失"

BLE 没法被动监听。手机连上灯之后，第二台 central 就挤不进去了。

突破口是广播行为：**BLE 外设在被连接后通常会停止广播。** 于是：

```
1. 我们的机器先连上真的 "downstair"   -> 真机停止广播
2. 我们的机器广播成 "downstair"        -> 手机只能看到我们
3. 手机连到我们                        -> 我们就在中间了
```

从这一刻起，手机写出的每个字节我们都能看到，真机的每个 notify 也都要经我们转发。

## 3. 方案 A — 用 macOS 冒充外设

拓扑：

```
 iPhone App  ──BLE──▶  Mac（CBPeripheralManager，广播 "upstair"）
                          │
                          │ Bleak（central）
                          ▼
                       真正的 "upstair" 灯
```

Mac 同时扮演两个 BLE 角色：

- `CBPeripheralManager` 广播 `FFE0` 服务、`FFE1` / `FFE2` 特征，接收手机的写；
- `BleakClient` 保持连接真机，把帧转发过去。

核心代码大概是这样：

```python
# 手机 -> 真机
def peripheralManager_didReceiveWriteRequests_(self, pm, requests):
    for req in requests:
        data = bytes(req.value())
        target = CHAR_FFE1 if req.characteristic().UUID() == CHAR_FFE1 \
                 else CHAR_FFE2
        tx_queue.put_nowait((target, data))

# 真机 -> 手机
def on_real_notify(sender, data):
    periph_delegate.notify_phone(bytes(data))
```

能用，但很不稳：

- macOS 偶尔起不来广播，或者重连后广播就没了；
- 代理还没起来时，手机可能又连回真机；
- iOS 会缓存 GATT，改了特征布局必须开关一次蓝牙；
- 同一个进程里同时跑 peripheral 和 central，时序问题很难复现。

## 4. 方案 B — ESP32 串口中继（最终采用）

稳定版把两个角色拆开：ESP32 负责外设侧，Mac 负责 central 侧，两者用 USB 串口通信。

```
 iPhone App ──BLE──▶ ESP32（广播 "downstair"）
                        │  USB 串口，行协议
                        ▼
                     Mac（Bleak central）──BLE──▶ 真正的 "downstair"
```

行协议（115200，一行一帧）：

| 方向 | 行 | 含义 |
|---|---|---|
| ESP32 → Mac | `TX_FFE1:aaafba03142a2e82` | 手机往 FFE1 写了这些字节 |
| ESP32 → Mac | `TX_FFE2:...` | 同上，FFE2 / AT 通道 |
| Mac → ESP32 | `RX:5550ba1000...` | 用这些字节 notify 手机 |
| ESP32 → Mac | `EVENT:PHONE_CONNECTED` | 状态事件 |

ESP32 那边的固件故意做得很"笨"：用同样的广播名、`FFE0`/`FFE1`/`FFE2`，
把手机的写打成 hex 打到串口，收到 `RX:` 就 notify 回去。
所有转发逻辑和日志都在 Mac 上，改起来、重放起来都方便。

为什么最终用它：

- ESP32 的广播行为确定，不受 macOS 状态影响；
- Mac 只维护一条 BLE 链路，没有角色冲突；
- 串口日志就是一份带时间戳的干净抓包；
- 重放很简单：把同样的 hex 用 Bleak 写给真机即可。

## 5. 第一次抓包：App 连上后干了什么

App 连上后立刻发校时：

```
[20:42:46] [ESP32] TX_FFE1:aaafba03142a2e82
[20:42:46] >>> FORWARDING TO REAL DOWNSTAIR: hex=aaafba03142a2e82
[20:42:47] <<< REAL DOWNSTAIR NOTIFY: 5550ba100001010d050101585e0101001200172d93
```

拆命令：

```
AA AF  BA  03  14 2A 2E  82
│  │   │   │   └─┬─┘ └┬┘  └ 校验和
│  │   │   │     │    └ 0x2E = 46 秒
│  │   │   │     └ 0x2A = 42 分
│  │   │   └ 0x14 = 20 点
│  │   └ BA = 校时
│  └ AF = 魔数
└ AA = 魔数
```

回包才是真正的收获：

```
55 50 BA 10 | 00 01 01 0D 05 01 01 58 5E 01 01 00 12 00 17 2D | 93
             └────────────────── 16 字节 ─────────────────────┘
```

| 字节 | 值 | 含义 |
|---|---|---|
| `[11]` | `0x58` = 88 | 流水亮度 |
| `[12]` | `0x5E` = 94 | 台阶亮度 |
| `[15]` | `0x00` | 模式 0（全亮） |
| `[16..19]` | `12 00 17 2D` | 定时 18:00 – 23:45 |

一次交互就把状态模型全暴露了：模式 + 两路亮度 + 内置定时，全都不用猜。

后面几帧同样有用：

```
AA AF B9 01 4F 62    -> 台阶亮度 0x4F = 79
AA AF B8 01 3F 51    -> 流水亮度 0x3F = 63
```

分别回了 `55 50 B9 01 00 5F` / `55 50 B8 01 00 5E`，
校验和与"单字节负载"的布局就此确认。

## 6. 补齐命令表

有了可用的中继，剩下就是系统性地试：

1. **看 App 的每个操作。** 一次只改一个变量（模式、每路滑块、定时），
   对比抓到的帧。
2. **从 ESP32 重放。** 用我们自己的代码发同样的字节，确认实体灯有反应。
   如果 App 能、我们不能，通常是校验和或长度算错了。
3. **扫未知操作码。** `brute_power.py` 用 `B0`–`BF` 加不同短负载逐个试，
   一边试一边盯着灯。日志里能看到 App 还用了 `B2`、`B4`、`B6`、`BB`、`BD`，
   但面板不需要它们。
4. **找开关命令。** 在这个范围里没有找到独立的开关操作码；
   最接近的是模式 `0`（全亮）。所以面板在向 HomeKit 暴露 light 实体时，
   用"台阶亮度 = 0"表示关灯。

## 7. 验证

最后一步才是关键：关掉手机 App、断开中继，让 ESP32 面板自己发。

```
AA AF B5 01 02 B7           -> 模式 2（流水）
AA AF B9 01 50 64           -> 台阶亮度 80
AA AF BE 04 12 00 17 2D 71  -> 定时 18:00–23:45
```

灯照做，就说明协议已经掌握到可以接管设备的程度了。

## 8. 踩过的坑

- **真机必须先停止广播。** 先连真机，再广播代理，否则手机可能连回真机。
- **同一时间只允许一个 central。** 控制器只接受一条连接；面板连着时，
  厂商 App 必须关掉。
- **iOS 会缓存 GATT。** 改了代理的特征布局后，先在手机上开关一次蓝牙。
- **校验和就是简单求和。** 错一个字节，控制器会静默丢弃——不报错、不回应。
- **notify 是唯一的反馈。** 有些命令会回一个短 ACK
  （`55 50 <cmd> 01 00 <chk>`），有些什么都不回，不要死等。
- **连接后的时序很关键。** App 在 1 秒内就发 `BA`；如果发得太早
  （notify 订阅还没就绪），回包就丢了。

## 9. 伦理

这些操作都在自己购买的设备上完成，目的只是替换一个已经没人维护的厂商 App。
同样的方法对很多 BLE 设备都有效——请只对自己的设备使用。
